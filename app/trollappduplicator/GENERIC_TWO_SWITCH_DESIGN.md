# 通用分身工坊：双开关最小改动设计

状态：设计方案，尚未实现、构建或安装通用版。
日期：2026-11-08。
适用前提：用户有权使用的IPA，现有安装方式为TrollStore；RootHide高敏App不注入、
不Hook、不附加调试器、不写插件到其沙盒，不做官方检测绕过。

## 1. 结论与范围

目标是任选App，由同一套引擎自动发现能力和规划改动，不为大麦、淘宝等分别编写共享组补丁。
本轮设计只保留用户要求的两个生成开关和既有导入功能，不顺便加入通知、钥匙串、
扩展身份或登录SDK改造。

通用的是分析和处理规则，不是承诺所有第三方App都会登录、支付或完整隔离成功。
无法安全迁移的输入给出具体限制，不静默降级，也不凭名字识别App是否兼容。

重要术语修正：当前删除的是URL回调注册CFBundleURLTypes，不是通知接收回调，
不关闭APNs或UIApplicationDelegate的远程通知处理方法。

## 2. 用户可见的操作

1. 导入IPA，或从已安装App列表选择代码包。加密主程序不可直接制作，工具不解密。
2. 输入新分身名称。每次新建使用新实例UUID、新Bundle ID，不沿用旧分身更新映射。
3. 设置两个独立开关：
   - 避免回调冲突：开启时移除主App的URL scheme注册；关闭时保持输入原样。
   - 共享组隔离：开启时自动发现并迁移可处理的App Groups；关闭时保持输入原样。
4. 显示简短生成前检查：共享组数量、能否处理、仍保留的风险。存在阻断项就不进入写包。
5. 生成IPA，不自动安装。报告保留在工具内部诊断区，不出现在普通文件列表中。

默认建议两个开关开启。每次确认时固定本轮选项；繁忙期间修改设置不改变已排队任务。
两个开关只影响新生成包，不原地修改旧包、已安装分身或原版。
重新安装同一份生成IPA仍然更新该IPA对应的分身，重新新建才会创建另一个身份。
本轮不新增隐式更新能力，后续若支持更新，必须单独选择已有实例，禁止按名称推断。

## 3. 四种组合的严格契约

| 避免回调冲突 | 共享组隔离 | 生成时的改动 | 必须说明的限制 |
|---|---|---|---|
| 关 | 关 | 只修改主Info.plist的分身Bundle ID、显示名称及对应本地化显示名称 | 最大限度保留输入；可能抢回调、共用组/钥匙串/扩展，不能叫隔离模式 |
| 开 | 关 | 基础新建改动，加移除主App的CFBundleURLTypes | 不竞争这类入站scheme；仍可能主动打开外部App，共享存储仍保留 |
| 关 | 开 | 基础新建改动，加已规划共享组名称/权限迁移和必要重签 | App Group有机会分开，但原回调和钥匙串身份冲突仍存在 |
| 开 | 开 | 两项改动的并集，不增加其它功能降级 | 不能由此保证通知、登录、支付、钥匙串及扩展容器全部独立 |

关闭意味着本轮从不可变输入不执行该变换，不是从已改过的分身包中猜测恢复旧值。
输入本身若已删除回调或已迁移共享组，关闭开关不会凭空恢复；UI显示实际输入状态。
同一选项清单中的本地化显示名修改也必须可逐项核对，不改其它本地化字符串。

### 两个开关都关是不是原版能力？

准确说法是：尽量保留输入包的原有实现和声明，退回原复制改名的兼容路径。
不是与官方原版完全等价，因为分身Bundle ID改变，主Info.plist改变使旧签名完整性不再成立，
TrollStore安装可能重签和调整容器配置。服务端/SDK资格、扩展ID、钥匙串及回调共存行为
也可能受影响。工具不能承诺所有功能恢复，也不能承诺不影响原版。

## 4. 架构：共用一套引擎，按能力分析

```text
IPAImport（保留现有文件接收/复制）
  -> PackageInventory（完整文件、嵌套组件、Mach-O和输入身份）
  -> CapabilityGraph（实际签名组权限、各组件的引用及关系）
  -> CloneInstance + ImmutablePlan（新身份、选项、替换映射、允许改动）
  -> PreflightGate（支持/无需处理/阻断/残留风险）
  -> CallbackTransformer + GroupTransformer（独立、按计划执行）
  -> SigningAdapter（只签本轮受影响的程序）
  -> ArtifactValidator（字节、权限、指令、加密及打包核对）
  -> IPA交付（安装/实际容器/功能验证是另外的阶段）
```

业务App名只用于展示，不能用于选择大麦/淘宝专用处理分支。
格式适配器可以区分Mach-O slice、C字符串、已知结构化资源或签名格式，不能把App名字
作为底层修补规则。暂不支持的格式留在能力报告中，不盲目全包替换。

## 5. 共享组自动发现和映射

### 5.1 完整组件清单

同时枚举主App、PlugIns、Extensions、Frameworks、dylib和嵌套App；不只看主程序。
从每个程序的实际代码签名读取application-groups，CPU slices必须语义一致。
embedded.mobileprovision仅辅助核对，不替代实际签名，不把它当运行时有效授权。
加密TEXT不代表无法读取LINKEDIT中的签名，但不能由可读签名推断加密代码的引用已知。

CapabilityGraph记录：
- 节点：程序、扩展、资源、共享组、应用身份。
- 边：哪个程序声明哪个组、哪个静态引用使用哪个名称、哪些组件应共享同一组。
- 风险旁路：相同扩展ID、原钥匙串身份、关联域/推送等；只提示，本轮不顺手重写。

### 5.2 支持零个、一个和多个组

- 没有声明或引用共享组：标为“未发现需迁移的App Group”，正常生成，不像当前实现硬报错。
- 多个组：分别映射，不能合并成一个组，否则会把本来分开的业务数据混在一起。
- 同包多个组件使用同一个旧组：必须映射同一个新组，保持分身内部的共享关系。
- 不同分身实例：使用不同映射；记录完整实例ID和映射，后续明确更新才能沿用。
- 新组不复制原版账号、设备标识、密钥或推送token，由App按自己的初始化流程填充。
- 没有原授予权限的组件不自动获得新权限；如果它必需访问组但缺权限，报告冲突。

### 5.3 组名不能再写死或凭后缀猜测

候选组名来源是实际授权和可解析引用，不是假定group.<Bundle ID>固定结构，
也不假定必须包含Team ID。大麦中的OS后缀只是既有实验事实，不推广为通用命名规则。

若发现授权集合之外的group样式字符串，它可能是别名、其它App的组、日志文案或默认配置。
必须分类其用途；不能自动为它新增权限或仅因为匹配group.正则就修改。
发现未解析的组引用，共享组开关开启时提示“引用覆盖未确定”，不宣称完整迁移。

### 5.4 安全写入策略

先规划所有组及所有目标程序，再改副本；同一程序若包含多个组，应用全部变换后只重签一次。
避免对多个组逐次重签，造成累计漂移或只按最后一项检查。

第一阶段只支持经过验证的完整C字符串常量和结构化资源精确字段：
- 不改指令，不在加密范围写入，不在代码签名中做原始字节替换。
- C字符串起点、NUL边界、section类型和长度必须可核对。
- 前缀重叠的组使用精确完整名称，不能group.A替换时误改group.AB。
- 同名常量若可能用于日志、网络请求或完整性校验，不把普通出现次数当用途证明。
- 等长变换先行，避免指针/文件布局迁移；不够长度或不能验证引用就拒绝。
- 新名称必须符合允许字符和长度约束，检查本批映射及已知实例/已安装组的冲突。
- 等长名称的可用空间不足以容纳足够随机熵时不退化成几位数字；初始设计门槛80位，
  是本工具候选准入策略而非Apple要求，无法满足则报告“不支持此名称长度”。
- 跨设备/全系统唯一性不能仅靠本地冲突检查保证；新实例UUID和足够随机空间降低碰撞风险。

后续不同字符串/资源格式增加格式适配器，不引入按App名字写死的替换清单。
一般性指针重定位、Swift常量表及复杂资源重写不进入首版；没有证据时宁可阻断。

## 6. 预检和降级边界

| 情况 | 处理 |
|---|---|
| 主程序加密、ZIP损坏、路径异常、缺必需文件 | 任何模式都拒绝；不是因为开关关闭就跳过基础安全校验 |
| 没有App Group | 该变换无需执行，显示“无App Group需迁移”，不宣称无任何共享机制 |
| 组权限和引用可解析、替换位置安全 | 生成静态验证候选；运行时隔离/功能另验 |
| 多slice布局可处理且权限一致 | 逐slice计划；未支持的slice格式明确阻断，不只修改一个slice |
| 组名动态构造、混淆、加密区域或用途不确定 | 开关开启时阻断迁移或标明需人工确认；不能认证已完全隔离 |
| 可选扩展无法迁移或仍加密 | 不自动删扩展；提示范围。保留它意味着不能声称所有组件组访问独立 |
| 共享组迁移不支持但用户想保留原行为 | 用户明确关闭共享组开关重新生成，不自动回退 |
| URL回调注册移除 | 不阻断出站授权，不生成新官方回调，不修改登录/支付SDK |
| Universal Links、钥匙串、扩展ID、推送存在重叠 | 残留风险，不隐藏、不自动塞进两项变换中 |

不能靠静态扫描证明所有动态引用完整；“支持静态处理”不等于“全功能和全数据隔离验证通过”。
没有原作者源码或运行验证时，这是通用离线处理能力的真实上限。

### 6.1 最小计划数据结构

```text
ClonePlan
  source_hash / source_version / parser_version
  instance_uuid / clone_bundle_id / display_name
  options: remove_url_registrations, migrate_app_groups
  components[]: path, binary_hash, slices, signed_entitlements
  group_map[]: old_group, new_group, declaring_components[], verified_references[]
  actions[]: component, exact_field_or_byte_range, expected_before, expected_after
  blockers[] / residual_risks[]
  allowed_changed_files[] / allowed_entitlement_keys[]
```

每次新建生成instance_uuid；开启共享组时基于instance_uuid与完整old_group生成新名称，
例如group.加允许字符编码的映射值，按旧名称字节长度分配空间。不能要求每个App都含
某个厂商前缀，也不自动批量替换Team ID。原名不同分别映射，同组所有声明者共享映射。
等长、格式、随机空间或冲突校验不满足则阻断，不用短后缀勉强输出。

四种模式共用同一个执行器，但严格按计划动作执行：关闭共享组时不加载GroupTransformer、
不调用其签名器，不因为“预检方便”给副本修改组权限。回调关闭时不删任何回调字段。
基础包读取/校验仍执行。计划缺动作的文件全部做内容哈希不变检查。

组名在资源、非C字符串section、脚本配置或签名外额外出现时，必须归入明确支持的解析器
或报告阻断，不能假定只有Mach-O cstring一种用法。加密程序即使可见某些组名，也只
证明可见部分，不能将加密代码内部可能构造的名称认证为已覆盖。

最终IPA和内部记录先写临时路径，全部检查完成再发布；失败不能留下成功标记或半成品。
任何降级需要用户重新确认选项，不在同一次执行中自作主张改变两个开关。

## 7. 回调开关的稳定性边界

这个开关通用且低侵入：移除主Info.plist的CFBundleURLTypes，不改其他字段。
但是它是有意降低外部返回能力，不是提高所有App的业务稳定性：

- 入站URL scheme不再竞争原版；外部授权/支付返回分身可能失效。
- 主动openURL、Universal Links等机制不因该开关被彻底关闭或独立化。
- 无CFBundleURLTypes时操作应为无变化，不报错。
- 不把通知扩展、APNs注册、通知授权或消息处理方法当作URL回调一起删除。
- 关闭保留原注册，但重复注册可能影响原版，不保证外部流程正常。

## 8. 什么叫“其余保留原能力”

两项变换之外不主动调整：
- 原始application-identifier、Team、钥匙串权限；同时警告访问重叠。
- 原扩展ID、扩展内容与数量；同时警告安装后扩展容器复用。
- aps-environment、后台、关联域、Apple登录、SDK客户端配置。
- 主程序逻辑、第三方框架、账号数据或推送身份参数。

保留是对生成时文件/声明的约束，不是原功能必然可用的保证。
任意签名身份不匹配、第三方SDK/服务端校验、原包裁剪资源均可导致失败，两个开关都关闭
也不会自动获得原作者的签名/域名/推送配置资格。保留权限不等于拥有有效服务资格。

## 9. 稳定性评估：不编造百分比

当前证据主要是一个App的实验，无法推导通用版稳定性为90%或99%。
仓库说明中记录过夹具和设备自检，但本次没有重跑；此前引用的research和evidence产物
当前本地路径已不存在，所以不能把历史数量当成这轮新完成的测试或可复核百分比。

需要分别统计：
1. 工具可靠性：不崩溃、失败可恢复、原输入不变、生成身份不重用。
2. 支持覆盖率：多少App/版本可按开启的选项完成预检和变换；拒绝不是功能成功。
3. 静态产物正确率：只有允许范围发生改动，重签后的非组权限和指令/crypt保持不变。
4. 业务兼容率：安装/启动/验证码登录/页面是否可用，不能从生成成功计算。
5. 共存隔离：原版是否保持正常，普通容器/组/扩展/钥匙串哪些已分开、哪些仍重叠。

质性判断：导入与基础改名可做到相对低风险；回调删除变换简单但外部功能明确受限；
共享组迁移是最高风险部分，需要保守能力门禁。开关都关时通常变换最少，但共存风险最大。
“最少改动”“最少共享”“业务最兼容”不是同一个方向，不能用单个稳定性分数替代。

建议的验证计划（未执行）：
- 至少20个App/版本，覆盖无组/单组/多组、多扩展、不同字符串格式、加密组件及各种身份结构。
- 每个输入4种组合，共80个组合；不支持项按理由保留在分母中，另外报告支持率。
- 生成器对同源/同名重复新建、选项切换、取消、异常输入/签名失败、目录冲突做独立检查。
- 基于相同固定输入与本轮明确实例，检查四种选项的差异；不同时改变身份来声称单变量归因。
- 包验证必须逐slice、逐权限、逐目标字节；对非目标文件要求哈希完全一致。
- 在具备授权和安全环境时逐App验证实际容器、安装和基本页面/登录，不让夹具代替第三方兼容。
- 用户不关心通知时它记为范围外，不标为已验证；金融/阿里/京东等遵守不注入边界。
- 出现原版数据/跳转退化就停止该样本，不自动重试、清数据或恢复全局配置。

没有执行这批验证前，只能给“设计风险等级”和已支持的格式，不能给真实成功概率。

## 10. 性能与资源

- 前台一次性任务，无daemon、无持续监听，不往分身增加常驻库。
- 输入复制、哈希和字符串扫描使用有界流式缓冲；单生成任务、并发数1。
- 一次构建清单，多个组统一扫描/规划，同一受影响程序最多重签一次。
- 输入内容hash、解析器版本、选项和实例ID组成缓存key；App版本号不替代文件hash。
- 只缓存不含凭据的结构/位置/权限信息；每次应用前再确认输入及目标字节没变。
- 损坏/不支持早拒绝，取消和失败清理本轮工作目录，不能清用户输出或账号目录。
- CPU/内存/耗时要实测，不承诺零内存、零耗电或签名工具峰值不变。
- App Group首启为空可能改变初始化成本；不加常驻代码不代表启动时间绝对不受影响。

## 11. 实施顺序与验收

1. 冻结当前手机工具作为可回退版本，只新增通用分析/计划模块，不改现有大麦实验默认路径。
2. PackageInventory/CapabilityGraph先实现任意授权IPA的只读分析和组关系提取。
3. CloneOptions/ImmutablePlan明确四种组合和非目标字节/权限契约，支持无组输入。
4. 拆分回调处理，改造GroupMigration为多组、完整名称、格式适配器处理，删除大麦/OS假设。
5. 先在本地做组合与负向检查，确认失败不修改源输入，没有静默共享回退。
6. 新构建通用预览工具，再在明确授权的设备验证，不能把设计文档当已安装交付。

通用预览准入：任意App都能被分析；支持项正常生成、阻断项有准确原因；4种选项的变换
范围可验证；新建从不读取旧更新映射；没有不必要设备/账号写入和通知/检测绕过改造。
全App业务稳定或全数据隔离不是首版准入承诺，用户看到能力和残留风险后决定是否安装。

## 12. 本轮实际结果

- 已阅读当前AppDuplicator、GroupMigration、CloneSettings和IPAImport源码确认实现边界。
- 当前共享组仍写死group.cn.damai.damaiApp及OS后缀；仅接受cn.damai.iphone输入，
