# 原版优先的独立 App 分身设计

状态：设计草案，未实现、未生成新分身、未安装验证。
日期：2026-11-08。
目标环境：可用签名/安装方式支持的 iOS；当前用户设备为 iPhone13,1 / iOS16.3.1 / TrollStore / RootHide。安装方式和权限必须以执行时现场结果为准。

## 1. 设计结论

实现一个前台、一次性运行的分身管理 App，负责读取授权安装包、分析身份冲突、生成最小独立副本和展示验收结果。副本直接作为系统注册的独立 App 运行，不在宿主容器中运行，不加入 dylib，不依赖 Crane 或越狱加载器。

优先级固定：

1. 原装 App 的代码、数据和正常功能优先。
2. 分身必须有可验证的独立身份与系统注册。
3. 无法独立提供的分身能力明确不支持。
4. 若必要能力无法安全降级，拒绝制作或交付该 App 分身，不保留冲突身份来换取“能打开”。

不承诺任何第三方 App 都支持多开、不承诺完全无法检测设备改动、不承诺同设备/同账号的服务端状态独立、不承诺零资源开销。对阿里/蚂蚁、京东、金融 App 不进行注入、Hook、调试附加、插件沙盒写入或检测绕过。

## 2. 为什么不能继续只改 Bundle ID

### 2.1 已有证据

此前读取的大麦9.0.38和分身cn.damai.iphone.37346：

- 普通数据容器和注册HOME不同。
- 存在18个重复URL scheme。
- App Group实际指向同一个可写共享目录。
- 分身仍使用原版application-identifier和container-required。
- 3个内嵌扩展ID重复，关联域、推送和登录能力也继续复用。

用户已报告：删除分身后，再执行原版同一登录跳转成功。这支持共存产生实际干扰，但没有单独定位唯一原因，不能把所有风险都当作已经发生的故障。

原始现场元数据见：`research/damai-clone-interference-audit-20261108/`。它是旧分身存在时的证据，不冒充删除后的当前设备状态。

### 2.2 解密与身份隔离是两个阶段

解密仅准备可处理的程序包。DumpDecrypter、TrollDecrypt不会代替分身进行完整的系统身份、权限和第三方业务适配。解密工具、分身打包器、安装器各自拥有独立输入/输出验收，禁止混成“成功生成IPA所以全部功能正常”。

## 3. 支持模式

| 模式 | 输入 | 能力 | 交付结论 |
|---|---|---|---|
| 源码支持模式 | 自有/授权源码及可用签名身份 | 编译独立身份，关闭功能入口，为允许的服务独立登记；重构共享组和路径 | 可按实际测试逐功能确认，控制力最高 |
| 二进制最小副本模式 | 授权使用、来源可信的未加插件IPA | 仅修改元数据/签名权限/可选组件，不改业务机器码，不注入 | 仅候选；必须证明目标App能接受能力降级 |
| 不支持 | 必须访问原版共享组、固定原版身份、必需外部回调、仍加密必要程序或缺失资源 | 不绕过、不强行输出 | 明确原因和替代方式 |

第一版只做二进制最小副本的检查/生成和自有测试App验证，不宣称已具备大麦兼容性。对第三方必需能力缺乏证据时按“不支持或需要授权人工验证”处理。

不能仅静态字符串搜索就认证没有硬编码身份。没有源码时，完整兼容性只能通过合法、范围受控的运行验证或目标开发者说明进一步确认。

## 4. 架构

```text
输入 IPA
   |
PackageInspector ---------> 原包完整性与能力报告
   |
IdentityPlanner ----------> 持久的副本身份映射
   |
CapabilityPlanner --------> 保留/移除/不支持清单
   |
PackageTransformer -------> 工作副本（不修改输入或原装App）
   |
SigningAdapter -----------> 可安装IPA + 签名/权限记录
   |
ArtifactValidator --------> 静态交付门禁
   |
InstallCoordinator -------> 用户授权后安装
   |
InstalledStateInspector --> 实际注册/容器/权限核对
   |
验收或停止使用并回滚副本
```

管理器不读账号凭据，不访问原版数据容器内容，不替用户登录或操作支付，不部署daemon，不全局重新注册系统App，不擅自修改RootHide白名单。受权限限制不能核对的项目标为未知，不以空结果代替通过。

## 5. 输入与解密验收

### PackageInspector

检查并保留：

- 源文件SHA-256、来源说明、版本/构建号、大小。
- ZIP CRC、压缩展开大小、重复条目、路径穿越、异常符号链接/硬链接，拒绝越界写入和解压炸弹。
- 主App、嵌套App、Framework、dylib、PlugIns/和Extensions/下所有.appex；不只扫描主程序或一个扩展目录。
- 每个CPU slice的架构、最低系统、加密标记、dylib依赖和代码签名状态。
- 必要资源、可选组件和现有第三方加载项。
- Info.plist、本地化显示名称、URL、文档类型、关联域、权限、App Groups、推送、后台能力。

判定原则：

- 主程序或必要框架仍加密：拒绝。
- 可选扩展加密/系统要求过高：只有用户明确同意降级且有依据证明可选时才排除；记为“移除”，不得记为“解密成功”。
- 缺少原始完整资源：标明设备裁剪/资源未知，不通过跨设备兼容验收。
- 已存在注入/功能改动：严格模式拒绝，改用可信基线；不盲删dylib，因为它可能有加载项和依赖。
- 不自动调用任何解密工具。软件包选择和实际解密另行授权，不将导出工具的权限带进副本。

## 6. 身份规划

### 6.1 持久副本ID

不要每次更新都生成随机Bundle ID。为每个分身实例创建一次持久标识，例如：

```text
instance_id: <UUID>
clone_bundle_id: com.ayao.clone.damai.<instance-token>
display_name: 大麦分身
```

示例ID只是设计占位，不是已注册或已验证可签名身份。实际格式由签名方式和目标平台校验。

同一个实例后续版本继续使用相同Bundle ID、签名身份、钥匙串命名空间与允许的共享组；不得每次变更后使系统创建新的账号容器。换签名身份等破坏性变化先提示可能需要重新登录，禁止无授权迁移原版账号数据。

### 6.2 签名与容器身份

处理每个独立运行的App/扩展，而不是只改顶层Info.plist：

- CFBundleIdentifier。
- 根据实际签名方式生成合法一致的application-identifier和必要Team信息。
- 副本使用适合该安装方式的独立容器身份。若存在旧字符串型container-required，不得继续保留原版值。
- 原版App Group和钥匙串访问组不进入副本授权集。
- 禁止通配钥匙串授权、不必要平台/无沙盒/调试权限、模仿原开发者私有权限。
- 管理器安装权限与副本权限分离；副本不继承管理器entitlement。

不能简单删除全部entitlement后让安装器补齐：TrollStore公开代码有宽泛的fallback签名配置，而且会保留已有字符串型container-required。必须使用受控非空权限集，并在安装后重新验证实际权限。

不把保留Team ID/伪签名当成得到原开发者APNs、Apple Sign In或关联域资格。不为躲避SDK检查伪装原身份。

## 7. 能力隔离策略

每个能力的状态只允许：`保留且独立`、`移除并降级`、`不支持`、`待验证`。待验证不等于通过。

| 能力 | 基础分身默认策略 | 需要说明的限制 |
|---|---|---|
| 原版URL scheme接收 | 不注册 | 不再竞争原版登录/支付/分享回调；外部授权返回不支持 |
| 副本自己的入口 | 可选，使用独有且无冲突的scheme | 原程序未必能处理任意新scheme，不必为新图标编造地址；可直接由系统图标启动 |
| 主动打开外部App | 不因删回调就称为已关闭 | LSApplicationQueriesSchemes是查询声明，不是出站总开关；代码仍可能调用openURL |
| Universal Links/Passkey域 | 不沿用原版associated-domains | 不改变原版AASA或Safari偏好；不保证所有链接/凭据行为自动按期望回退 |
| 原版App Group | 不授权 | 硬编码组名可能返回nil并让副本失败；无法正常降级则拒绝，不开放原组 |
| 副本App Group | 基础无扩展时不创建；需要时独立配置 | 只改权限不会改业务代码组名；必须源码支持或有明确兼容依据 |
| 钥匙串 | 独立最小访问组，禁止原组与通配组 | 有些SDK指定旧组名；受控权限可拒绝访问，但不保证登录逻辑继续工作 |
| 扩展/嵌套App | 基础模式排除经确认可选组件 | 必要扩展必须独立身份/容器及关联；禁止机械删除所有.appex |
| APNs/后台推送 | 不保留原版推送资格、remote-notification及通知扩展 | 申报移除不等于UI中所有通知代码停止；副本可不可用，原版不动 |
| Apple Sign In等身份绑定服务 | 基础不承诺/不沿用原资格 | 源码模式可以移除入口；二进制模式不能仅改plist就隐藏按钮或改服务逻辑 |
| iCloud/文档handler/扩展服务 | 不复用原容器或冲突handler | 必须检查目标实际声明；没有声明不需要顺带修改 |
| 相机、照片、位置等TCC | 副本正常向系统申请，原版授权不迁移 | 不读写TCC数据库，不保证改变签名后授权表现不变 |
| Cookie/Web认证/剪贴板 | 不复制账号会话，不hook公共服务 | Safari认证cookie、剪贴板、同一账号服务端会话不随Bundle ID完全隔离 |
| 自动保活/后台管理 | 不提供 | 不能保证两个App一直后台存活；iOS调度限制仍适用 |

### 7.1 两个必须避免的虚假保证

**删回调不等于禁出站。** 基础分身可以不抢原版回调，但仍可能主动跳转淘宝/支付宝，授权结果可能回原版。若要彻底避免分身触发原版授权链：

- 有源码：在副本构建配置中关闭这些登录/支付入口，保留支持的App内登录方式。
- 无源码：明确标记这些入口不可用；仅当目标已有可选内部入口且用户接受限制时验证候选，不能认证误操作也绝不会影响原版。如果要求完全强制禁止这类动作而不改代码/不注入，则目标可能不支持。

**删App Group权限不等于业务无共享依赖。** 需要的原版组访问被拒绝后，副本可能打不开或无法登录。必须验证nil/失败路径，不以“打不开原数据所以方案成功”交付。

## 8. 包转换与签名

PackageTransformer只在本地独立工作目录操作，不直接复制写回安装中的原App路径。输入包保持只读，输出不覆盖输入。

维护明确的变更集：

- 修改了哪些Info.plist键和本地化显示名。
- 删除/保留的可选组件和理由。
- 每个签名对象的身份/entitlement差异。
- 不改的代码和资源SHA-256。

SigningAdapter支持不同合法可用的签名/安装路径，功能隔离逻辑与具体工具解耦。使用参数数组启动固定签名工具，不使用含用户名/路径的shell字符串拼接，不嵌入凭据。

签名按照内嵌组件至主App顺序；不采用“先把所有权限原样复制”或“只重签主程序”捷径。不将移除资源签名文件当成整包签名已有效。

只新增身份/元数据处理代码，不自动剥除商业授权、修改SDK校验、绕过服务端限制或引入身份伪装Hook。能力适配有版本化配置，但它是生成器使用的元数据策略，不是运行时注入插件。

## 9. 产物门禁

打包前后必须通过：

1. ZIP目录安全、CRC、CPU与目标最低系统符合声明。
2. 没有未声明的必要加密对象/资源缺失。
3. 输出主App和保留扩展身份均唯一且与签名一致。
4. 原版scheme、关联域、App Group和原钥匙串组不在输出授权/注册集中。
5. 没有新增dylib加载、全局Hook、越狱路径和不必要调试/无沙盒权限。
6. 变更范围与用户选定能力降级清单一致，其它代码和资源保持不变。
7. 副本Bundle ID不等于原版/系统App/其它实例，签名器和安装器不允许force替换原版。

通过静态门禁仅输出“可安装候选”，不是“功能完整”或“不会影响原版”的认证。

## 10. 安装事务与安装后验收

### 10.1 状态机

```text
DISCOVERED
  -> ANALYZED
  -> PLAN_CONFIRMED
  -> PACKAGED
  -> ARTIFACT_VALIDATED
  -> INSTALL_AUTHORIZED
  -> INSTALLED_NOT_VALIDATED
  -> STATIC_ISOLATION_VALIDATED
  -> FUNCTIONAL_ACCEPTED

任何失败 -> STOPPED / ROLLBACK_PENDING
```

每个状态包含证据，失败不推进到成功状态。不用安装器返回0替代实际注册和权限检查。

### 10.2 原版基线

安装前记录原版包哈希清单、身份、实际注册路径、普通容器、共享容器映射、扩展注册和相关权限。不读取账号/文件内容；不能取得基线或原版功能本来异常时不开展验收。

原版相同登录跳转需由用户确认正常，截图/日志脱敏。真实认证、验证码、支付、账户数据变更不得被自动化隐式执行。

### 10.3 安装操作

- 只允许用户明确授权后调用已核实的安装方式。
- 单任务串行安装，不同实例不能同时改系统注册。
- 路径转换集中在InstallCoordinator；RootHide SSH视图与TrollStore视图需现场确认，不把路径字符串当作同一文件。
- 保留输入包、输出包、当前副本回滚包及变更报告。首次安装无需备份不存在副本的数据，更新已有副本前先按授权做副本备份。
- 不修改RootHide配置，不自动开启任何目标白名单，不改TrollStore注册策略来冒充普通App Store安装。

### 10.4 未启动前检查

重新读取安装后的实际签名、entitlement、LaunchServices：

- 副本容器与原版不同，实际组映射不共享原组。
- 没有恢复原URL schemes/域名/扩展身份/钥匙串授权。
- 没有安装器fallback增权或保留旧容器值。
- 原版代码、元数据、容器和预期注册不变量未变化。

不满足即标记未通过，不启动副本、不让用户继续登录；提出仅回滚/卸载副本的明确操作并在执行前获得授权。安装本身会改变系统注册，因此不能承诺未经检查的短暂状态完全没有影响。

公开安装器逻辑只能作为辅助，实际安装后结果优先。此前观察到的独立普通容器不证明所有数据途径均独立。

## 11. 功能验收与范围

以下是设计验收计划，不是本轮已执行的测试：

| 场景 | 必须满足 |
|---|---|
| 原版跳转 | 无副本时正常；装副本后同一入口仍正常，目标正确 |
| 原版内容链接/分享 | 原来的入口和返回目标不被副本改变 |
| 副本登录 | 只测试已允许的方式；账号与原版是否独立不能只看首页 |
| 两个独立账号 | 副本退出不影响原版；使用授权的测试账号，不清原版登录状态 |
| 共享组/钥匙串 | 验证副本无原组授权及正常失败处理；不读取原版条目作为测试材料 |
| 通知/扩展 | 原版不受影响；副本禁用的功能不作为承诺，通过独立声明验证 |
| 更新 | 相同实例ID和数据身份保持，能力新增或策略变化需重新确认 |
| 卸载副本 | 不以原版身份卸载，不清共享组/原版钥匙串，原版继续正常 |
| 重启/系统注册变化 | 两份状态和独立容器稳定；不自动通过全局uicache修复 |
| 开销 | 不在目标App增加运行时Hook/轮询；管理器退出无持续任务 |

存在第三方固定身份或同账号服务端会话策略时，技术上可能无法做到全功能隔离。只能给有证据支持的功能贴兼容标签，未知/不支持不能隐藏。

## 12. 更新、卸载和数据保护

- 更新重新跑全包扫描，防止新版本增加扩展、URL scheme、共享组或更高系统要求。
- 新版本继承同一实例ID，签名方式改变影响数据访问时不得默默继续。
- 回滚不降级覆盖原装App，不使用原App Bundle ID；副本数据格式是否支持版本回退单独验证。
- 卸载前明确提醒副本本地数据风险，按精确副本ID调用官方路径；禁止手工清组容器、钥匙串或系统注册数据库。
- 管理器只清理自己生成的临时目录，进程中断后按manifest找残留，不扫描删除其它App或用户媒体。
- 不复制原版账户、照片权限或共享数据。用户需要迁移自有副本数据时另行设计备份/恢复契约。

## 13. 性能与存储

原则：消耗主要发生在制作阶段，不向目标App追加常驻执行逻辑。

- 解压、扫描、哈希和签名在后台工作线程，UI只更新节流进度；单个任务串行写入。
- 用流式I/O，初始设计buffer上限1MiB，按文件处理，不把整个100MiB以上IPA读入内存。
- Hash和目录扫描尽量合并遍历；限制同时处理对象数，取消后关闭文件并释放资源。
- 工作空间估算：保守预留展开大小的2倍加输出大小/余量；不以固定“几百MB”判断所有App。
- 初始管理器峰值额外工作内存目标不超过32MiB；这是目标，实际压缩库/签名工具峰值必须测量，不声称已经达到。
- 管理器关闭后无daemon、定时器、App保活或自动登录；副本自身仍是完整App进程，运行第二份一定会增加内存/CPU/网络消耗。
- 副本的实际存储可能包含一份代码、独立资源和独立数据，文件克隆/去重不当作稳定节省保证。
- 打开速度不增加运行时Hook成本，但重签、缓存、资源和能力降级仍可能改变启动表现；用实际冷启动对照验证，不承诺“绝对不慢”。

记录不含账号、token、验证码、钥匙串值和密码。签名/安装权限只能在可信本地接口托管，不写入manifest。

界面四步即可：

2. 命名副本，显示降级列表和是否有无法隔离的必需能力。
3. 生成包并展示完整检查结果；静态失败时不提供安装按钮。
4. 用户授权安装，先核对静态隔离，再展示允许的验收步骤，最终按功能标记支持范围。

不能用一个绿色“成功”代表打包、安装、隔离和全部业务功能都通过。

## 15. 建议实施顺序

### 阶段一：先做检查器，不装新分身

输入已授权包，生成身份/依赖/系统注册风险清单和能力移除计划。复用已有IPA解析研究，但修正为安全流式读取并明确错误状态。输出可读报告，不改变输入或手机。

### 阶段二：用自有测试App验证整个机制

制作一个有URL callback、App Group、钥匙串和可选扩展的测试App。建立源码独立变体，证明身份、升级、卸载和权限拒绝处理；避免直接用高敏生产App试错。

### 阶段三：生成二进制最小副本候选

实现能力白名单、变化报告和签名适配；没有源码支持的主动外部登录关闭，不伪造已完成。对于硬编码旧身份/共享组且无法正常降级的App拒绝。

### 阶段四：批准后安装与验收

先对非高敏授权目标完成只读基线、事务安装与原版不变量/功能核对。大麦类高敏目标不通过注入或调试修补，只有满足既定边界及有充分兼容依据的候选才考虑后续授权步骤。

此阶段划分不是当前已有功能。必须保留管理器和测试App可维护源码、Makefile/构建配置、签名/打包脚本与版本化策略，不能只交IPA。

## 16. 交付标准

可以交付：独立分身候选、明确移除能力、逐文件/权限变更记录、安装后身份报告、原版不变量与实际功能验收记录。

不能交付为保证：任意App通用、多账号服务端完全独立、登录/支付/推送全保留、零资源开销、完全非越狱状态或绝对检测不到。

对于本次需求，最短正确方案是：原版不动 + 严格最小副本 + 独立身份 + 不复用注册/可写共享能力 + 安装后门禁；不是继续换砸壳软件。
